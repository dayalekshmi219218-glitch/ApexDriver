# ApexDriver Web (UI prototype)

A working React front end for ApexDriver: sign in, add vehicles, upload a trip log, get a health report with
severity colors, see trends and unusual scans across scans, ask for a plain-English explanation, and compare vehicles
on a ranked dashboard.

**Everything behind the screens is simulated in the browser** (sign-in, analysis, explanations, storage). The point of this
step is to see and judge the product before the backend exists. The simulator sits behind one interface
(`src/services/api.ts`), so the real FastAPI + Supabase backend replaces it without touching any screen.

## Run it

Needs Node 18 or newer.

    npm install
    npm run dev          # http://localhost:5173

Click **Try the demo** on the login page. It loads three synthetic vehicles (12, 10 and 5 scans) so every screen has data.
"Continue with Google" is simulated and creates an empty account.

Other commands:

    npm test             # 20 unit tests (scoring, anomaly detection, explanations, demo data)
    npm run build        # type-check + production build
    npm run preview      # serve the production build on :4173
    python3 scripts/gen-theme.py   # regenerate src/theme.css from the token table and re-check WCAG contrast

## What is real and what is simulated

| Piece | Status in this prototype |
|---|---|
| Screens, navigation, dialogs, charts, PDF download | Real |
| Per-signal scoring, time-in-range, overall score, engine-state split | Real code (TypeScript), runs on the series it is given |
| Unusual-scan detection (robust z-score vs the vehicle's own history) | Real code, needs 8+ scans |
| In-trip jump markers (running-average outliers) | Real code |
| Explanation text | Template-built from structured facts. The numbers are checked against the evidence, as the real LLM output will be |
| Google sign-in | Simulated |
| Uploaded file contents | **Not parsed.** The file is only checked (CSV, under 10 MB, readable header); the report is then generated by the simulator |
| Demo vehicles and scans | Synthetic, generated from parameters. Nothing is copied from any real dataset |

## Where the backend plugs in

`src/services/api.ts` defines the `Api` interface and `mockApi`. Replace `export const api = mockApi` with an
implementation that calls the backend:

| Api method | Backend |
|---|---|
| `signInWithGoogle`, `getSession`, `signOut` | Supabase Auth (Google) |
| `createVehicle`, `updateVehicle`, `deleteVehicle`, `listVehicles` | Supabase with row-level security (deleting a vehicle cascades to scans) |
| `uploadScan` | `POST /scans` then poll status ("processing" then "ready") |
| `listScans`, `deleteScan` | `GET /scans`, `DELETE /scans/{id}` |
| `explainScan`, `explainChart` | `POST /scans/{id}/explain`, `POST /charts/explain` (LLM, same JSON shape as `Explanation`) |
| `exportData`, `deleteAllData` | `GET /me/export`, `DELETE /me/data` |

The shapes in `src/lib/types.ts` (`Scan`, `SignalSummary`, `Explanation`, ...) are the contract the Python side should return.

## Scoring notes (read before porting to Python)

The scorer is a port of the Android `ScoreCalculator`, with these deliberate differences (each is covered by a test):

1. **Missing signals are not scored as healthy.** The overall score only uses signals that had data, and the report states "based on N of M".
2. **Low-direction bands are interpolated.** In the Android code, the "low" branch never interpolates (its guard `to > from` is always false),
   so every value in a low-moderate band scored a flat 60. Here it interpolates 100 to 60 like the high branch.
3. **Weakest-link blend.** Overall score = 60% weighted mean + 40% worst scored signal, because a plain weighted mean lets one failing
   signal hide behind healthy ones.
4. **Alert cap.** While any scored signal is in Alert (1% or more of its time in the alert zone), the overall score is capped at 79
   so the gauge never says "Normal" next to an Alert row.
   Points 3 and 4 differ from the approved spec text (plain weighted mean); change `WEIGHTED_MEAN_SHARE` and `ALERT_CAP` in
   `src/lib/scoring.ts` to revert.

Other rules: coolant is scored only after warm-up (70 C); battery, rpm and intake air only while running (rpm above 600);
a signal is Alert at 1% of time in the alert zone and Watch at 5%; anomaly detection stays off below 8 scans and only flags
changes in the unhealthy direction. All thresholds live in `src/lib/config.ts`.

## Data and licensing

Do not commit or deploy real dataset files. The Kaggle "Car ECU Datalogs" page (author gxkok21) shows "Data files (c) Original Authors",
which is not an open license. Public demos should use the synthetic vehicles; real files stay local or are uploaded by the user.

## Structure

    src/lib/        scoring, config (bands and weights), anomaly detection, explanations, synthetic data, units
    src/services/   api.ts  <- the swap point for the backend
    src/state/      store.tsx (app state, settings, toasts)
    src/components/ gauge, range bar, charts, explain card, upload, PDF, shell
    src/pages/      Login, Dashboard, Vehicles, VehicleDetail, Report, Analytics, Settings
    src/theme.css   generated design tokens (light and dark)
    src/test/       unit tests

## Known limitations

- Data lives in the browser (localStorage); clearing site data removes it.
- The PDF library is about 1.3 MB but only loads when someone clicks Download PDF.
- Only the English locale and metric/imperial temperature are supported; speed units are stored but no current signal uses them.
- Explanations are templates until the LLM is connected.
